I maintain forks of three code formatters, [oxfmt-next-line](https://github.com/motlin/oxc-next-line), [prettier-next-line](https://github.com/motlin/prettier-next-line), and [prettier-java-next-line](https://github.com/motlin/prettier-java-next-line). They do one thing differently from upstream: opening braces go on their own line.

## How to use them

All three forks add a `braceStyle` option with two values. `next-line` is the default. `same-line` gives you upstream's output, so you can switch back without changing tools.

### Oxfmt

`oxfmt-next-line` is a fork of [Oxfmt](https://oxc.rs/docs/guide/usage/formatter), the Rust formatter from the Oxc project. It formats JavaScript, TypeScript, JSON, CSS, SCSS, Less, GraphQL, and YAML. It installs both an `oxfmt-next-line` command and an `oxfmt` command, and it reads the usual `.oxfmtrc.json`.

```json
{
	"braceStyle": "next-line",
	"useTabs": true,
	"printWidth": 120
}
```

I install it with [mise](https://mise.jdx.dev/) and run it from [pre-commit](https://pre-commit.com/).

```toml title=".mise/config.toml"
[tools]
"npm:oxfmt-next-line" = { version = "0.75.0", allow_low_downloads = true }
```

```yaml title=".pre-commit-config.yaml"
- id: oxfmt
  name: oxfmt-next-line
  entry: oxfmt-next-line --no-error-on-unmatched-pattern
  language: system
```

### Prettier Java

`prettier-java-next-line` is a fork of [prettier-plugin-java](https://github.com/jhipster/prettier-java). Prettier resolves plugins from the working directory, so when the plugin is installed by mise, I load it by path.

```toml title=".mise/config.toml"
[tools]
"npm:prettier" = "3.9.10"
"npm:prettier-java-next-line" = { version = "2.11.4", allow_low_downloads = true }
```

```yaml title=".pre-commit-config.yaml"
- id: prettier-java
  name: prettier-java-next-line
  entry: sh -c 'prettier --plugin "$(mise where npm:prettier-java-next-line)/node_modules/prettier-java-next-line/dist/index.mjs" --write "$@"' --
  language: system
  types: [java]
```

If you use [Spotless](https://github.com/diffplug/spotless), it expects a package named `prettier`, so use an npm alias for `prettier-next-line`. The [README](https://github.com/motlin/prettier-java-next-line) has the full Maven configuration.

### Edge cases

Next-line braces need a few exceptions to stay correct.

- `return {` stays together in JavaScript, since moving the brace would change what the program does through automatic semicolon insertion.
- An empty `{}` stays on one line.

## Why

The usual argument for same-line braces is that they save vertical space, which mattered on small, low-resolution CRT displays where every row counted.

I started my career writing C++, where my team consistently used next-line braces. I later learned the wider C++ community was always split on brace style, but next-line braces influenced Microsoft, and today the one big community where they're the official default is C#. I saw first-hand that the convention was better, even on the small monitors of the early 2000s. On a modern display, I'd rather spend one extra line and see the shape of the block.

With next-line braces, every opening brace lines up with its closing brace.

## Why now?

Next-line braces have always made sense to me. What's new is that forking a formatter is cheap now. LLMs are good at writing formatters, and when they run one, their diffs aren't full of formatting noise.

Our jobs have changed too. We barely write code by hand anymore, but we review it all day, every day, skimming as fast as we can. Anything that improves readability, like vertically aligned braces, matters more than ever.

## Undermining Prettier's philosophy

Prettier is deliberately opinionated. Its [option philosophy](https://prettier.io/docs/option-philosophy) says "Prettier has a few options because of history. But we won't add more of them." The point is to end debates about style.

That makes sense, but only if the choices are right, or at least right enough. Quotes are a good example. `singleQuote` is one of the few options Prettier has. On [Syntax](https://syntax.fm/show/794/prettier-javascript-with-vjeux/transcript), co-creator Christopher Chedeau said double quotes came from James Long's own habits, while most of the industry uses single quotes, and they've kept the default only to avoid a breaking change. That's roughly the bar for an option: the default turned out wrong, and most people want the opposite. Personally, I could use either quote style and not care much.

On the same episode, when asked for Prettier's most controversial default, Chedeau named curly braces.

Still, next-line braces don't clear that bar. They aren't the most common style, and most of the community isn't asking for them. I think that's partly because the community has worked without next-line braces as a choice for decades. Even newish languages and tools like rustfmt don't give next-line as a choice. But I think brace placement matters enough to be configurable.

People have asked for a brace style option before ([#3832](https://github.com/prettier/prettier/issues/3832), [#3964](https://github.com/prettier/prettier/issues/3964), [#4212](https://github.com/prettier/prettier/issues/4212)), and all of those issues were closed. I [proposed a `braceStyle` option](https://github.com/jhipster/prettier-java/pull/840) to Prettier Java, keeping same-line as the default. The maintainer turned it down, politely and for consistent reasons: K&R is the dominant style in Java, and new options go against Prettier's goal of avoiding style debates. That's a fair position for an opinionated formatter, and it left me with one option: fork it.

There's some irony here. In 2018 I wrote that if I started a long debate about tabs versus spaces and curly brace placement, people would rightly be upset with me for wasting their time. I still believe that. A consensus is good, and ending the debate is the point of a tool like Prettier. Making brace placement configurable, and arguing for it in a blog post, undermines that. But I used next-line braces for the first years of my career, and once you get used to them, they're much, much better.

## How I built it

Maintaining forks of a Rust formatter with 19 native build targets, Prettier, and Prettier Java would not have been worth it for one person a few years ago. LLMs made it possible to build the forks and to keep them current. Each fork releases at the upstream version number, and I have recurring tasks scheduled for LLMs that merge each upstream release, run the tests, and prepare the next release. It hasn't been expensive in terms of my time.

Once you own a formatter, braces aren't the only thing you fix. The Java fork also has options to keep a wrapped list's closing parenthesis on its last line, keep short array initializers on one line, group imports the way Spotless does (so I could drop that Spotless step), and break `throws`, `extends`, and `implements` clauses onto their own lines.

The same rule now extends past source files. In [Liftwizard](https://github.com/liftwizard/liftwizard/pull/4328), Jackson's pretty printer puts a nested object's opening brace on the next line, matching what oxfmt-next-line does to JSON files.

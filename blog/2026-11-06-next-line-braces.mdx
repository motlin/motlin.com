The problem with opinionated code formatters is their opinions. The problem with writing your own is that it undermines the whole premise of avoiding debate.

Anyway, I forked three code formatters just so I could put curly braces on their own lines.

- [prettier-next-line](https://github.com/motlin/prettier-next-line), a fork of Prettier, which formats JavaScript and TypeScript.
- [prettier-java-next-line](https://github.com/motlin/prettier-java-next-line), a fork of Prettier Java, which is the first one I wanted to fork.
- [oxfmt-next-line](https://github.com/motlin/oxc-next-line), a fork of Oxfmt, which is newer and formats a whole bunch of languages. It mostly replaces Prettier, except where you need Prettier plugins like Prettier Java.

## How to use them

Upstream, none of the three let you configure brace placement, to prevent exactly this sort of debate. My forks add a `braceStyle` option and default it to `next-line`. I think that should be the default, so of course you should never touch this setting. But if you want, you can set it back to `same-line`.

### Oxfmt

`oxfmt-next-line` installs an `oxfmt` command too, and reads the usual [Oxfmt](https://oxc.rs/docs/guide/usage/formatter) `.oxfmtrc.json`.

```json
{
	"braceStyle": "next-line",
	"useTabs": true,
	"printWidth": 120
}
```

I install it with [mise](https://mise.jdx.dev/) and run it from [pre-commit](https://pre-commit.com/).

```toml title=".mise/config.toml"
[tools]
"npm:oxfmt-next-line" = { version = "0.75.0", allow_low_downloads = true }
```

```yaml title=".pre-commit-config.yaml"
- id: oxfmt
  name: oxfmt-next-line
  entry: oxfmt-next-line --no-error-on-unmatched-pattern
  language: system
```

### Prettier Java

`prettier-java-next-line` is a fork of [prettier-plugin-java](https://github.com/jhipster/prettier-java). Prettier resolves plugins from the working directory, so when the plugin is installed by mise, I load it by path.

```toml title=".mise/config.toml"
[tools]
"npm:prettier" = "3.9.10"
"npm:prettier-java-next-line" = { version = "2.11.4", allow_low_downloads = true }
```

```yaml title=".pre-commit-config.yaml"
- id: prettier-java
  name: prettier-java-next-line
  entry: sh -c 'prettier --plugin "$(mise where npm:prettier-java-next-line)/node_modules/prettier-java-next-line/dist/index.mjs" --write "$@"' --
  language: system
  types: [java]
```

If you use [Spotless](https://github.com/diffplug/spotless), it expects a package named `prettier`, so alias `prettier-next-line` to `prettier` in npm, as the [README](https://github.com/motlin/prettier-java-next-line) shows.

## Why

The case for same-line braces has always been vertical space. On an 80x25 terminal, I buy that. But when I started my career in 2005, computer monitors were already big enough for my team to use next-line braces with room to spare.

We were writing C++, and my team consistently used next-line braces. I later learned the wider C++ community was always split on brace style, but next-line braces influenced Microsoft, and today the one big community where they're the official default is C#. I saw first-hand that the convention was better. On a modern display, I'd rather spend one extra line and see the shape of the block.

With next-line braces, every opening brace lines up with its closing brace.

## Why now?

Next-line braces have always made sense to me. What's new is that forking a formatter is cheap now. LLMs are good at writing formatters, and when they run one, their diffs aren't full of formatting noise.

Our jobs have changed too. We barely write code by hand anymore, but we review it all day, every day, skimming as fast as we can. Anything that improves readability, like vertically aligned braces, matters more than ever.

## Undermining Prettier's philosophy

Prettier is deliberately opinionated. Its [option philosophy](https://prettier.io/docs/option-philosophy) says "Prettier has a few options because of history. But we won't add more of them." The idea is that nobody argues about style anymore. I like that idea, as long as the defaults are good.

Quotes are a good example. `singleQuote` is one of the few options Prettier has. On [Syntax](https://syntax.fm/show/794/prettier-javascript-with-vjeux/transcript), co-creator Christopher Chedeau said double quotes came from James Long's own habits, while most of the industry uses single quotes, and they've kept the default only to avoid a breaking change. As far as I can tell, that's what it takes to get an option in Prettier. The default has to be wrong, and most people have to want the opposite. Personally, I could use either quote style and not care much.

On the same episode, when asked for Prettier's most controversial default, Chedeau named curly braces.

Still, next-line braces don't clear that bar. They aren't the most common style, and most of the community isn't asking for them. I think that's partly because the community has worked without next-line braces as a choice for decades. Even newish languages and tools like rustfmt don't give next-line as a choice. But I think brace placement matters enough to be configurable.

People have asked for a brace style option before ([#3832](https://github.com/prettier/prettier/issues/3832), [#3964](https://github.com/prettier/prettier/issues/3964), [#4212](https://github.com/prettier/prettier/issues/4212)), and all of those issues were closed. I [proposed a `braceStyle` option](https://github.com/jhipster/prettier-java/pull/840) to Prettier Java, keeping same-line as the default. The maintainer said no, and was nice about it. Most Java code is K&R, and Prettier doesn't want new options that restart style debates. Honestly, that's the right call for Prettier. So I forked it.

The irony isn't lost on me. In 2018 I wrote that if I started a long debate about tabs versus spaces and curly brace placement, people would rightly be upset with me for wasting their time. I still believe that. A consensus is good, and ending the debate is the point of a tool like Prettier. Making brace placement configurable, and arguing for it in a blog post, undermines that. But I used next-line braces for the first years of my career, and once you get used to them, they're much, much better.

## How I built it

Maintaining forks of a Rust formatter with 19 native build targets, Prettier, and Prettier Java would not have been worth it for one person a few years ago. LLMs made it possible to build the forks and to keep them current. Each fork releases at the upstream version number, and I have recurring tasks scheduled for LLMs that merge each upstream release, run the tests, and prepare the next release. It hasn't been expensive in terms of my time.

Once you own a formatter, braces aren't the only thing you fix. The Java fork also has options to keep a wrapped list's closing parenthesis on its last line, keep short array initializers on one line, group imports the way Spotless does (so I could drop that Spotless step), and break `throws`, `extends`, and `implements` clauses onto their own lines.

The same rule now extends past source files. In [Liftwizard](https://github.com/liftwizard/liftwizard/pull/4328), Jackson's pretty printer puts a nested object's opening brace on the next line, matching what oxfmt-next-line does to JSON files.
